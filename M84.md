# Quhip — V1 Plan for M84 (copy as-is)

Copy this entire file to M84 as-is. Do not split it into phases, do not ask for clarification first, and do not drop any v1 must-have to make the build smaller. If a requirement below conflicts with an existing file, library, or platform limit, stop on that item and report the conflict instead of silently changing the requirement.

## 1. Goal in one sentence

Build Quhip, a Hono API on Cloudflare Workers that replaces invasive Google Analytics: cookieless, privacy-first web analytics with click/scroll heatmaps, automatic element CTR, and full session/attribution metrics — where the site owner keeps their own data.

## 2. What Quhip is / is not

- IS: a self-hostable analytics API + tiny JS snippet + dashboard, for any website. First customer is Michael's own portfolio (his TehWiz sites), then other site owners.
- IS NOT: Google Analytics. No Google code, no Google account, no cross-site tracking, no advertising IDs.
- IS NOT: a session-replay tool. There is no playback of a visitor's session, no mouse-trail replay, no screen recording.
- IS NOT: a user-tracking tool. There are no user profiles, no cross-day or cross-site identities, no individual visitor journeys in the dashboard.

## 3. Stack (locked)

- Hono (TypeScript) on Cloudflare Workers. Hono is the edge-native fit: tiny core, Web Standards Request/Response, no Node-only APIs in the Worker path.
- pnpm exclusively. Never npm or Bun for this project.
- Storage: Cloudflare D1 for aggregated tables (see §8). Do not introduce a separate database server, Redis, or paid analytics backend for v1.
- Dashboard: served from the same Worker project (Workers Assets or the Worker itself serving the dashboard app). One deployable project, not two services to keep in sync.
- New project. Do not bolt this onto Pico, Casper, TehWiz, or any other repo. Do not modify any other project's code, prompts, or layout to build Quhip.

## 4. Privacy hard lines — non-negotiable, failure conditions

Any one of these being violated is a failed build, even if everything else works:

1. No cookies. The snippet must never set, read, or depend on a cookie, first-party or third-party.
2. No fingerprinting. No canvas/WebGL/audio fingerprinting, no font enumeration, no battery/network probing to identify a device, no combining of signals into a stable device ID.
3. No IP storage. The Worker may use the request's country/region from Cloudflare edge headers for coarse geography, but must never write an IP address (full or truncated) to any table, log, or file.
4. No cross-site or cross-day identity. A session ID (see §5) must never be reused across sites, and must never persist across days or browser restarts.
5. No personal data in events. Never capture: input values, textarea content, password fields, contenteditable content, form submissions' contents, email addresses, names, search query terms, or free-form text that could be user-generated.
6. No session replay, keystroke capture, or text capture. Heatmaps are aggregated click/scroll counts only (see §7).
7. No click IDs. Never store `gclid`, `fbclid`, `msclkid`, `twclid`, or any other ad click identifier, from URLs or referrers.
8. No raw per-visitor event log retained. Ingest aggregates immediately (see §8) and does not keep a queryable log of individual visitors' events. If a temporary buffer is needed for batching, it must be short-lived (minutes, not days) and must not be exposed in the dashboard.
9. No pre-checked consent. See §10. A pre-ticked permission box anywhere in Quhip is a failure, full stop.
10. No Google Analytics code, SDK, or beacon anywhere in Quhip, the snippet, or the dashboard.

## 5. Sessions and time — exact definitions (use these, do not invent others)

- Session ID: an ephemeral ID generated in `sessionStorage` on first pageview of a tab. It dies when the tab closes. It is never written to a cookie, `localStorage`, or any persistent store, and never sent across sites. A new tab = a new session. A returning visitor tomorrow = a new session, with no link to yesterday's.
- Session timeout: 30 minutes of inactivity ends a session. Activity = a pageview, a click, or a scroll-depth milestone while the tab is visible.
- Active time (the only time Quhip reports): time when the tab is visible AND the visitor was active (mouse, keyboard, scroll, or touch) within the last few seconds. Wall-clock time with a tab open in the background does not count. Use the Page Visibility API plus throttled activity listeners, and flush on `pagehide` / `visibilitychange` to hidden.
- Time on page: active time on that page, per session, summed across sessions for averages. Report median as well as average — averages alone hide the "left the tab open" skew, even with active-time filtering.
- Session duration: sum of active time across all pages in that session.
- Pages per session: pageviews in the session, counting each page once per load (SPA route changes count as pageviews, see §6).
- Bounce: a session with exactly one pageview AND no meaningful interaction (no click, no scroll past 25%, no goal) AND under 10 seconds of active time. A single-page session that clicked something or scrolled deep is not a bounce.
- Bot filtering: the snippet is a JS beacon, so non-JS crawlers never register. Additionally, ignore known bot user-agents and headless signatures server-side, and ignore sessions under 1 second of active time with no interaction. Do not count bot traffic in any metric.

## 6. V1 must-have metrics — all of them, none deferred

Every metric below is v1. No metric in this section may be moved to v2 to save time.

Traffic:
- Pageviews (per page, per site, per date range)
- Sessions (per site, per date range)
- Approximate uniques: distinct session IDs per day, per site — labelled "daily sessions", never presented as identified people

Engagement:
- Active time on page (average + median, per page)
- Session duration (average + median)
- Pages per session (average)
- Bounce rate (per page and per site, using the §5 definition)
- Scroll depth: average max scroll %, and % of sessions reaching 25% / 50% / 75% / 100% of page height, per page

Interaction:
- Total clicks (per page, per site)
- Clicks per pageview
- Element CTR (see §7)
- Outbound link CTR: clicks on links leaving the site, divided by pageviews of the linking page
- Dead clicks: clicks on elements that produce no navigation, no visible change, and no goal — counted per element, so broken UI surfaces on its own
- Rage clicks: 3+ clicks on the same element within 2 seconds, counted as rage-click events per element (do not let rage clicks inflate normal click CTR — report them separately)

Flow and outcome:
- Entry pages (first page of each session, counted per page)
- Exit pages (last page of each session, counted per page)
- Top paths: the most common 2- and 3-page session paths, aggregated only. Suppress any path with fewer than 5 sessions in the selected range — small counts must not be shown, because they could identify a single visit. Never show an individual session's path.
- Goals: site-owner-defined goals (see below), with goal count and goal conversion rate = sessions completing the goal / total sessions in range

Context (coarse only):
- Referrer domain (see §9) and UTM/campaign (see §9)
- Device: coarse device class (desktop / mobile / tablet, from viewport + user-agent class, never a specific device model used as an identifier) and viewport bucket
- Browser class (Chrome / Firefox / Safari / Edge / other — family only, no version fingerprinting)
- Country: coarse country from Cloudflare edge headers only, never city, never IP-derived location beyond country

Goals (v1, simple):
- A goal is defined in the dashboard as: a click on a specific element (by `data-quhip` label or selector), a visit to a specific page path, or an outbound click to a specific domain.
- Goals count sessions completing them, not raw events. A session completing the same goal twice counts once.
- Goal contents are never captured: a form-submit goal records that a submit happened, never what was submitted.

## 7. Automatic element click tracking + heatmaps — the epic CTR data

This is a headline v1 feature, not an add-on. No manual event tagging may be required to get element data.

Automatic capture:
- One delegated click listener on `document`. It must catch dynamically added content and SPA route changes with no re-binding and no per-element code on the site owner's side.
- On each click, identify the element in this priority order:
  1. `data-quhip` attribute value, if present (site owners add this to key CTAs for a stable, human-readable name, e.g. `data-quhip="signup-btn"`)
  2. Element `id`, if present and not obviously random/hashed
  3. `aria-label`, if present
  4. Generated selector path (tag + stable classes + structural position), as a fallback only
- Record per click, server-side, aggregated by (site, page path, element identity): total clicks and sessions-that-clicked. Both numbers must be stored and shown — sessions-that-clicked is the CTR numerator, total clicks is not, so rage clicks cannot inflate CTR.
- Element views: use IntersectionObserver to count sessions in which an element became visible (at least 50% visible). Element CTR = sessions-that-clicked-the-element / sessions-that-saw-the-element. This is the primary CTR. Clicks / pageviews is a secondary, clearly-labelled figure only, because it understates below-the-fold and modal elements that most visitors never see.
- Element CTR table (dashboard): per page, one row per element, with element label, element views, sessions clicked, CTR, total clicks, rage-click count, and dead-click flag where applicable. Sortable by CTR and by clicks.
- Outbound elements: links to another domain are elements too — they appear in the same table, flagged as outbound, with their destination domain (never full destination URL with query strings).
- Hashed-class caveat: if a site uses hashed CSS-module class names that change every deploy, auto-generated selectors will churn and the same button will appear as a new element after each deploy. Mitigate with the `data-quhip` priority above and document it in the snippet README — do not try to "fix" this by fingerprinting or by storing element text content.

Heatmaps:
- Click heatmap: aggregated click coordinates per page, normalised to page/viewport coordinates, rendered as an overlay on the page (or on a captured layout skeleton — do not screenshot or store the visitor's actual page content with user data in it).
- Scroll heatmap: aggregated scroll-depth distribution per page, rendered as a scroll-depth overlay / depth chart.
- Heatmaps are aggregates over the selected date range and page. There is no per-session, per-visitor, or replay view. Minimum-count suppression applies here too: do not render a heatmap from fewer than 5 sessions for that page in range — show "not enough data" instead.

Privacy guards for element tracking (in addition to §4):
- Ignore clicks inside `input`, `textarea`, `select`, password fields, and `contenteditable` elements entirely. Do not record them, do not count them.
- Do not capture element text content that could be user-generated (a username link, a post title, a comment). Labels come from `data-quhip`, `id`, `aria-label`, or structural selector only.
- Any element, or subtree, with `data-quhip-ignore` is never tracked for clicks, views, or heatmap coordinates. Document this attribute as the site owner's opt-out for sensitive areas.
- Never capture the href query string of a clicked link. Store destination domain only for outbound links, and path only for internal links.

## 8. Snippet + ingest API + aggregation

Snippet (the JS a site owner pastes in):
- Tiny, async, non-blocking. Aim for under 10 KB gzipped. One script tag, one site key, no other configuration required for default tracking.
- Batches events and sends with `sendBeacon` (with `fetch` with `keepalive` as fallback). Flush on `pagehide`, on visibility change to hidden, and periodically during long sessions. Never block navigation waiting for a beacon.
- Handles SPA route changes (History API) as new pageviews without a full reload.
- Respects `data-quhip-ignore` subtrees and the consent state (see §10): if the site owner enabled the banner and the visitor has not consented, the snippet must not send any event at all — not even a pageview.
- Must not set cookies, must not read cookies, must not use `localStorage` for identity. `sessionStorage` only, for the ephemeral session ID in §5.
- Must degrade silently if the API is unreachable: no console spam, no errors shown to visitors, no retries that hammer the API.

Ingest API (Hono routes, conceptually):
- `POST /api/event` — accepts a batch of events, requires a valid site key, validates shape and site, rejects unknown sites and malformed batches with a 4xx and no storage. Rate-limit per site key to prevent abuse and runaway bills.
- Event payload fields (only these, reject anything else): site key, session ID (ephemeral, §5), event type (pageview / click / scroll / goal / element-view), page path (no query string), element identity (per §7, no text content, no href query), viewport bucket, device class, browser class, referrer domain, UTM fields (per §9), timestamp (server time is authoritative — do not trust client timestamps for aggregation).
- Dashboard API routes are separate from ingest routes, require owner authentication, and must never accept a site key as a read credential. A site key is ingest-only.
- Owner authentication for the dashboard: implement a minimal, real auth (not "anyone with the link can view"). Cloudflare Access or a password-based owner login is acceptable — pick one, implement it fully, and document it. Do not ship an unauthenticated dashboard.

Aggregation and storage (D1):
- Aggregate on ingest into counter tables keyed by (site, date, page, element, referrer, campaign, etc.). Do not store a row per visitor event as the queryable dataset.
- Daily and hourly rollups are acceptable; raw buffered events, if any buffering is used, must be short-lived and must not be dashboard-visible.
- Small-count suppression: any dashboard query that would reveal a count under 5 sessions for a path, element, or segment must return "not enough data" for that row, not the small number.
- Time handling: store UTC, display in the dashboard viewer's timezone. Date ranges are by the site's local date as configured in the dashboard, defaulting to the viewer's timezone if unset — document which one is used, do not silently mix them.

## 9. Referrer + UTM attribution

- Capture once per session, at entry (first pageview of the session): referrer domain only, plus `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content` from the landing page URL.
- Attribution is first-touch for the session: internal navigation never overwrites it, so a session is credited to where it actually came from.
- Referrer handling: store domain only (e.g. `google.com`, `tiktok.com`). Never store the full referrer URL, path, or query string. Never store search query terms from referrer URLs.
- Page path handling: store path without query string. UTMs live in their own fields, not glued to the URL.
- Strip on ingest, never store: `gclid`, `fbclid`, `msclkid`, `twclid`, and any other ad click identifier, plus every other query parameter except the five UTM fields above.
- Channel grouping (dashboard): direct/none, search, social, referral, email, paid (from `utm_medium` values like `cpc`, `paid`, `ppc`). Search is grouped by domain only — never by search term.
- Dashboard attribution views: sessions by source, sessions by source/medium, sessions by campaign, landing page by source, and goal conversion by source/campaign. All aggregated, all subject to the small-count suppression in §8.

## 10. Consent banner — the right way, no pre-checked anything

Default: NO banner. Quhip is cookieless and aggregated, so by default there is nothing to consent to, and no banner should appear or block any content. This is a feature, not a gap — do not add a banner by default "just in case".

Optional banner (site-owner setting, off by default):
- Placement: bottom of the viewport, in the thumb zone, with safe-area padding, never covering the whole screen, never blocking content until dismissed.
- Timing: first session only, only if the site owner enabled it. If the visitor already made a choice, do not show it again unless they open the consent settings.
- Toggles: every granular permission toggle starts UNCHECKED. No pre-checked boxes, ever, in any state, including after "Accept All" is used for other categories — a toggle is checked only because the visitor checked it.
- Buttons: Accept All and Reject All, equally prominent (same size, same visual weight, no dark-pattern sizing or colouring). Accept All is a button the visitor actively taps — it is not a substitute for pre-checking the toggles.
- Gating: if the banner is enabled and the visitor has not consented, the snippet sends NOTHING. No pageview, no click, no "anonymous" event before consent. After Reject All, likewise nothing is sent.
- Changing your mind: the choice must be easy to change later (a persistent, small consent-settings control the site owner can enable), and withdrawing consent stops all future sending immediately.
- Consent record: store only the choice itself (accepted categories + timestamp), first-party, for the purpose of honouring it. Do not use the consent record as a tracking identifier.

## 11. Dashboard — what the site owner sees

- Site management: create a site, get a snippet + site key, see a list of their sites. One owner, many sites — the portfolio use case is first-class, not an afterthought.
- Overview per site, per date range: pageviews, sessions, bounce rate, average + median active time on page, average session duration, pages per session, top pages, top referrers, top campaigns.
- Element CTR table per page (see §7), sortable, with element views, sessions clicked, CTR, total clicks, rage clicks, dead-click flag.
- Heatmap view per page: click overlay + scroll-depth view, with the minimum-count rule in §7.
- Attribution views (see §9) and goals view (goal count + conversion rate, by source/campaign where counts allow).
- Entry/exit pages, top paths (aggregated, suppressed under 5 sessions), scroll-depth chart per page.
- Filters: date range, site, page, source/campaign. No filter may produce an individual-visitor view — if a filter combination would narrow to a single session, show "not enough data".
- The dashboard must never show: IP addresses, individual session IDs, individual click trails, form contents, search terms, or full URLs with query strings.

## 12. Out of scope for v1 (do not build these, even if they look easy)

- Session replay, mouse-trail replay, screen recording
- Individual visitor profiles, cross-day/cross-site identity, user journeys
- Funnels beyond the aggregated top paths in §6 (full multi-step funnel builder is v2, not v1)
- A/B testing, experiments, personalisation
- Search CTR (Quhip cannot see search impressions — do not fake this metric)
- Email reports, Slack alerts, or any notification system (dashboard only for v1)
- A public API for third parties to query other people's sites (owner-only dashboard for v1)

## 13. Build order (implement in this order, deliver complete v1, do not stop for approval between steps)

1. Hono Worker skeleton + D1 schema for aggregated tables + site-key validation + rate limiting.
2. Snippet: pageview, session (sessionStorage), active time, scroll depth, SPA handling, batching + sendBeacon, bot filtering.
3. Ingest aggregation for traffic + engagement metrics (§5, §6) + dashboard overview.
4. Referrer + UTM attribution (§9) + attribution views.
5. Automatic element tracking + element CTR table + dead/rage clicks (§7).
6. Heatmaps (click + scroll overlays) with minimum-count suppression.
7. Goals (definition in dashboard, counting in ingest, conversion views).
8. Optional consent-banner module (§10), off by default, fully gated — no event before consent when enabled.
9. Dashboard polish: site management, filters, date ranges, "not enough data" states everywhere suppression applies.
10. Dogfood: install Quhip on at least one of Michael's own sites alongside (not replacing, until verified) his existing analytics, and compare pageviews/sessions for sanity — report any large discrepancy, do not silently trust the first numbers.

## 14. Verification — run before reporting done (all of these)

- Build passes, no new errors, snippet under 10 KB gzipped (or report the actual size and why if it cannot meet this).
- Privacy audit, with evidence, not just assertion: grep the codebase and the built snippet for cookie reads/writes (`document.cookie`, `Set-Cookie`), fingerprinting APIs, IP storage, and Google Analytics references — all must be zero, except the consent record in §10 and the explicit "no Google Analytics" check. Show the grep results.
- Metric math tests with synthetic data: a scripted session with known pageviews, active time, clicks, and element views must produce exactly the expected pageviews, sessions, bounce (or non-bounce), scroll-depth %, element CTR, and goal conversion in the dashboard. Report the test inputs and outputs.
- Element CTR test: a below-the-fold element seen by few sessions must NOT show pageview-denominator CTR as its headline number — it must show the element-view denominator from §7.
- Consent test: with the banner enabled and no choice made, zero events reach ingest. After Reject All, zero events. After Accept All, events flow. After withdrawing, events stop. Toggles start unchecked in every test run.
- Attribution test: a session arriving with `utm_source` + a referrer, then navigating internally, must keep its first-touch attribution — internal pages must not overwrite it. A URL with `gclid`/`fbclid` must arrive in storage with those fields absent.
- Aggregation test: a path or element with fewer than 5 sessions in range must show "not enough data", not the small count.
- Performance test: snippet load must not block page rendering, and a page with the snippet must not show a measurable render delay attributable to Quhip in a basic before/after check — report the numbers, do not claim "fast" without them.
- Report when done: what was built (routes, tables, snippet, dashboard views), the verification results above, any requirement you had to deviate from and why, and the dogfood comparison from step 10. Do not report v1 as done if any §4 hard line, any §6 must-have metric, or any §10 consent rule is unmet.
